## 卡片1：User Story 快速自检

```
┌─────────────────────────────────────────────────────┐
│           User Story 快速自检卡                       │
├─────────────────────────────────────────────────────┤
│ ✓ 必检项（INVEST核心三角）                            │
│                                                       │
│   V - Valuable（有价值）                              │
│   └─ 角色是真实受益方（不是技术岗位）                  │
│   └─ 价值具体可排序（不是"更好""更快"）                │
│                                                       │
│   S - Small（足够小）                                 │
│   └─ 一个迭代内可讨论并推进                           │
│   └─ 不包含多个独立目标                               │
│                                                       │
│   T - Testable（可测试）                              │
│   └─ 能想象如何验证（不是纯形容词）                    │
│   └─ 给AC留出清晰的验收接口                           │
│                                                       │
├─────────────────────────────────────────────────────┤
│ ❌ 常见错误信号                                       │
│                                                       │
│  • 技术任务伪装成Story                                │
│    "作为后端工程师，我要改API返回码..."               │
│                                                       │
│  • 把实现细节写进Story                                │
│    "使用Redis缓存""调用XX接口"                        │
│                                                       │
│  • 价值用万能词                                       │
│    "更方便""更好的体验""更快"                         │
│                                                       │
│  • 一条Story包含多个目标                              │
│    "搜索、对比、收藏、分享..."                        │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 记忆口诀                                           │
│                                                       │
│  Story讲"为什么" → AC讲"怎么验" → Tasks讲"怎么做"    │
│                                                       │
└─────────────────────────────────────────────────────┘
```

## 卡片2：EARS 模式速查

```
┌─────────────────────────────────────────────────────┐
│              EARS 五种模式速查卡                      │
├─────────────────────────────────────────────────────┤
│ 1. Ubiquitous（通用型）- 无条件约束                   │
│    句型：The [system] shall [response].              │
│    场景：全局政策、基础约束                           │
│    示例：The Identity Service shall log every        │
│          failed authentication attempt.              │
│                                                       │
│ 2. Event-driven（事件驱动型）- 瞬间触发               │
│    句型：When [event], the [system] shall [response].│
│    场景：用户动作、外部事件                           │
│    示例：When the user submits a query, the Search   │
│          Service shall return results within 500ms.  │
│                                                       │
│ 3. State-driven（状态驱动型）- 持续状态               │
│    句型：While [state], the [system] shall [response]│
│    场景：登录态、运行模式                             │
│    示例：While the user is authenticated, the App    │
│          shall display the real-time balance.        │
│                                                       │
│ 4. Unwanted（异常处理型）- 失败场景                   │
│    句型：If [unwanted], then [system] shall [response│
│    场景：异常、超时、错误输入                         │
│    示例：If the backend does not respond within 3s,  │
│          then the App shall display a placeholder.   │
│                                                       │
│ 5. Optional（可选功能型）- 配置开关                   │
│    句型：Where [feature], the [system] shall [resp.] │
│    场景：可选功能、feature toggle                     │
│    示例：Where biometric login is enabled, the App   │
│          shall present fingerprint authentication.   │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 选择技巧                                           │
│                                                       │
│  When  = 瞬间触发（点击、提交、调用）                 │
│  While = 持续状态（登录中、运行中）                   │
│  If    = 异常处理（超时、失败、错误）                 │
│  Where = 可选功能（开关、配置、平台）                 │
│                                                       │
│ ⚠️  停止信号：前置条件超过3个 → 改用Decision Table    │
│                                                       │
└─────────────────────────────────────────────────────┘
```

## 卡片3：升级决策速查

```
┌─────────────────────────────────────────────────────┐
│            何时升级需求表达层次？                      │
├─────────────────────────────────────────────────────┤
│ 从 Story → EARS（契约层）                             │
│                                                       │
│  信号1：异常路径本身很重要                            │
│  信号2：NFR需要明确阈值和统计口径                     │
│  信号3：系统边界和接口责任必须讲清                    │
│  信号4：高风险行为需要review和追踪                    │
│                                                       │
│  示例：手机银行余额显示                               │
│  Story → "主页直接显示余额，方便查看"                 │
│  EARS  → "While authenticated, shall render balance  │
│           within 1s. If timeout, shall show          │
│           placeholder and log event."                │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 从 EARS → Decision Table（决策层）                    │
│                                                       │
│  信号1：前置条件超过3个                               │
│  信号2：规则组合形成网状结构                          │
│  信号3：需要验证覆盖完整性                            │
│                                                       │
│  示例：个性化推荐Feed                                 │
│  EARS不够 → "When 登录 AND 订阅有效 AND 未欠费 AND    │
│              大陆 AND iOS14+ AND 同意协议..."         │
│  Decision Table → 用表格列举所有条件组合              │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 从 EARS → State Model（状态层）                       │
│                                                       │
│  信号：状态切换复杂，单句描述容易失真                  │
│                                                       │
│  示例：订单状态流转                                   │
│  EARS不够 → 需要描述10+种状态转换                     │
│  State Model → 用状态机图表达                         │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 黄金法则                                           │
│                                                       │
│  不要过度形式化！只在边界真正重要时才升级。           │
│  轻量项目停在Story+AC就够了。                         │
│                                                       │
└─────────────────────────────────────────────────────┘
```

## 卡片4：EARS 质量检查

```
┌─────────────────────────────────────────────────────┐
│              EARS 质量快速检查卡                      │
├─────────────────────────────────────────────────────┤
│ 检查项          ✓ 合格信号         ❌ 危险信号        │
├─────────────────────────────────────────────────────┤
│ 主语            明确的系统/子系统   "页面""体验"      │
│                                     "应该被"          │
│                                                       │
│ 条件            显式写出，可观察    "合适时"          │
│                                     "必要时"          │
│                                                       │
│ 响应            带阈值/判据/输出    "尽快""更好"      │
│                                     "适当"            │
│                                                       │
│ 复杂度          1-2个条件           3+个条件嵌套      │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 修复方向                                           │
│                                                       │
│  主语模糊 → 找到真正的系统主语                        │
│  条件不清 → 明确触发条件或状态                        │
│  响应太虚 → 补充可测量的标准                          │
│  过度复杂 → 拆分或改用决策表                          │

```

## 使用建议

### 1. 打印贴墙
把这些卡片打印出来，贴在工位附近，随时查阅。建议使用 A4 纸打印，每张卡片占半页。

### 2. 团队培训
在需求评审会前，用这些卡片做快速培训。每次会议开始前花 5 分钟过一遍相关卡片。

### 3. 自检工具
写完需求后，用对应卡片检查一遍：
- 写完 Story → 用卡片1自检
- 写完 EARS → 用卡片2选模式，用卡片4检查质量
- 判断是否升级 → 用卡片3
- 规划PM成长路径 → 用卡片6
- 判断用原型还是文档 → 用卡片7
- 学习AI生成原型 → 用卡片8

### 4. 新人入职
作为新人的快速参考手册，配合主文档一起使用。

### 5. 会议速查
在需求评审、技术评审、验收会议时，把相关卡片投屏或分享给参会者。

## 卡片7：原型与文档的分工

```
┌─────────────────────────────────────────────────────┐
│        原型 + 文档：互补而非替代                       │
├─────────────────────────────────────────────────────┤
│ 用原型表达（视觉和交互）                              │
│                                                       │
│  ✓ 页面布局和导航结构                                │
│  ✓ 交互流程（点击、滑动、展开）                      │
│  ✓ 视觉反馈（loading、hover、disabled）              │
│  ✓ 表单字段和输入控件                                │
│  ✓ 响应式布局和适配                                  │
│  ✓ 基础的前端逻辑（显示/隐藏、简单校验）             │
│                                                       │
│  示例：                                               │
│  "点击提交按钮后显示loading，3秒后跳转到结果页"      │
│  → 直接在原型里演示，不需要文字描述                  │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 用文档表达（业务逻辑和约束）                          │
│                                                       │
│  ✓ 业务规则和计算逻辑                                │
│    "订单金额 = 商品价格 × 数量 - 优惠券 + 运费"      │
│                                                       │
│  ✓ 异常处理和降级策略                                │
│    "If 支付网关超时3秒，then 显示重试按钮并记录日志" │
│                                                       │
│  ✓ 性能和安全要求                                    │
│    "P95响应时间 < 500ms，密码必须加密存储"           │
│                                                       │
│  ✓ 权限和访问控制                                    │
│    "仅VIP用户可见高级筛选，普通用户显示升级提示"     │
│                                                       │
│  ✓ 数据校验规则                                      │
│    "手机号必须11位，邮箱必须包含@和域名"             │
│                                                       │
│  ✓ 状态机和复杂流程                                  │
│    "订单状态：待支付→已支付→配送中→已完成→已取消"   │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 黄金法则                                           │
│                                                       │
│  如果能"看到"或"点击" → 用原型展示                   │
│  如果需要"计算"或"判断" → 用文档说明                 │
│                                                       │
│  原型回答：这个功能长什么样？怎么操作？               │
│  文档回答：这个功能怎么算？什么情况下怎么处理？       │
│                                                       │
│  ⚠️  关键：原型和文档必须同时提供，缺一不可           │
│     原型没有文档 → 业务逻辑不清楚                    │
│     文档没有原型 → 交互体验难理解                    │
│                                                       │
└─────────────────────────────────────────────────────┘
```

## 卡片8：PM使用AI工具生成原型的快速指南

```
┌─────────────────────────────────────────────────────┐
│         PM如何用AI工具生成原型？                       │
├─────────────────────────────────────────────────────┤
│ 推荐工具（按学习曲线排序）                            │
│                                                       │
│  1. v0.dev (Vercel)                                  │
│     • 最简单：纯文字描述即可生成                      │
│     • 适合：快速验证想法，生成静态页面               │
│     • 限制：复杂交互需要手动调整                     │
│                                                       │
│  2. Bolt.new                                         │
│     • 中等难度：生成完整的可运行应用                  │
│     • 适合：需要前后端联调的原型                     │
│     • 优势：可以直接部署和分享                       │
│                                                       │
│  3. Cursor + Claude                                  │
│     • 较高难度：需要基础代码知识                      │
│     • 适合：需要精细控制的复杂原型                   │
│     • 优势：最灵活，可以深度定制                     │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 快速上手步骤（以v0为例）                              │
│                                                       │
│  Step 1：描述需求                                     │

│                                                       │
│  Step 2：生成并预览                                   │
│  AI生成代码 → 实时预览 → 看到可交互的页面            │
│                                                       │
│  Step 3：迭代调整                                     │

│                                                       │
│  Step 4：导出分享                                     │
│  导出代码 → 部署到Vercel → 分享链接给团队            │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 💡 写好AI提示词的技巧                                 │
│                                                       │

│  ❌ 避免技术细节："使用React Hooks和Tailwind"        │
│     （AI会自动选择技术栈）                            │
│                                                       │
├─────────────────────────────────────────────────────┤
│ 🎯 PM需要掌握的最小技能                               │
│                                                       │
```
